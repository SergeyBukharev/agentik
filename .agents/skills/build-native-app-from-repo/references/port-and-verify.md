# Port and verify

## Service and state

- Read the request and response shape of the deployed API, including errors, expiry, refresh or revocation, and any cookie, bearer token, CSRF, or origin requirements. GitHub Pages serves static files. Resolve the actual API base to the separately hosted HTTPS service when applicable. Use the correct endpoint for development, staging, and release. Inspect code and configuration names without reading or printing secret values. Use mock or authorized test credentials and endpoints for validation.
- Accept access codes in the UI and send them to the server for validation over HTTPS without persisting the codes. Use the session mechanism the server issues after validation. Use Expo SecureStore or an equivalent Keychain/Keystore-backed implementation for persistent token material. In a wrapper, verify the underlying security of any native storage bridge or use suitable server-managed cookies. Store larger local data separately. Handle token expiry, sign-out, secure-store read failure, and restart without leaking credentials through logs, links, bundle variables, or fallbacks. Treat `EXPO_PUBLIC_*`, `VITE_*`, app manifests, app assets, and compiled JavaScript as public.
- Preserve the source retention policy for saved profile data. For Agentik, verify the 90-day local TTL and its renewal triggers in code. Store state per profile with expiry and schema version. Test restart, profile switching, expiry, and migration from older supported app data. The server session has its own lifetime. Browser data lives in another storage sandbox, so a cross-client transfer needs an authorized sync or export/import path.
- Define offline behavior per operation. Bundle the shell and static data, restore cached history and drafts, and show when AI or remote rooms need a connection. Reuse existing IDs or idempotency contracts for retry and reconnect. Keep demo/local rooms local unless the verified backend supports member permissions and cross-device sync.

## Build and verify

1. Check the lockfile, package manager, project Node requirement, and the chosen framework's current version matrix. Use a supported Node LTS that meets the project constraints. For local Android builds, verify the compatible JDK, Android SDK/ADB, Gradle and device or emulator. For local iOS compilation or Simulator, use macOS with compatible Xcode and the selected dependency tooling. Physical iOS installation also needs an appropriate signing team and provisioning. On Windows, finish the feasible work and identify the exact iOS steps requiring a Mac. Use a hosted build only with authorization to upload source and use the account or budget.
2. For a local Expo development build, use the version-appropriate Expo toolchain such as `npx expo run:android` or `npx expo run:ios` once prerequisites are ready. Expo Go is suitable for compatible early previews. Verify native modules and deep links with a development build. Distinguish a debug APK that needs Metro, an APK that opens without Metro, an Android App Bundle for Play, and an iOS Simulator versus device artifact. Test an app requested as standalone with the dev server stopped. Local debug signing is part of a debug install. Use release signing credentials only when authorized. Confirm identifiers, versions, permissions, and store requirements when preparing an authorized release.
3. Run the project's relevant type checks and tests. On the target runtime check installation and launch, login failure and success, sign-out/reopen, the requested core flow, saved state and expiry, offline/reconnect, deep links/back, and keyboard where applicable. Use an API address reachable from the target: Android Emulator typically uses `10.0.2.2` for the development host, while a physical device needs a reachable LAN or HTTPS endpoint, or an appropriate ADB reverse port. Keep development networking exceptions out of release configs.
4. Report the verified source SHA and environment, build commands and artifact paths, and the platform, OS, build mode, and device type actually exercised. Label a web preview, emulator or Simulator, and physical-device results explicitly. Identify deferred steps and missing access, toolchains, or devices.
